## 二、先把问题复现出来（4 轮真实接口测试）

搜索**不计入下载配额**（官方：搜索没有限制，只有下载有），所以诊断可以放开打。
4 轮打下来，把用户那句模糊的抱怨变成了几条硬数据。

### ① 同一个查询，带不带年份是两个世界

用 `The Matrix` 当样本（它正好有纪录片 + 两部续集，是最恶劣的混淆现场）：

| 查询 | 接口返回的前几名 |
| --- | --- |
| `query=The Matrix` | **The Matrix Revisited (2001)** / Revolutions (2003) / Reloaded (2003) …… |
| `query=The Matrix` + `year=1999` | **The Matrix (1999)** —— 50 条**全是正主** |

`The Matrix Revisited` 是一部**纪录片**，`Revolutions`/`Reloaded` 是第二、三部。
真《黑客帝国》的 50 条候选里**一条都没有**，续集靠 28.8 万下载量把位置全占了。

### ② 换排序也不行（这条实测否掉了我的一个设想）

我本来怀疑"强制按下载量排序"是元凶，于是对比了接口默认的相关性排序：

| 查询 | 相关性排序 | 下载量排序 |
| --- | --- | --- |
| `The Matrix` | Revisited / Revolutions / Reloaded | 一模一样 |
| `黑客帝国` | Reloaded / The Matrix | 一模一样 |
| `2012` | Coldplay 演唱会 / 维密秀 | 一模一样 |

**两种排序的结果逐条相同。** 换排序救不了 —— 问题出在接口返回的候选集合本身，
不在我们怎么排它。

### ③ 没有年份时，连"挑条数最多的"都是错的

| 文件名（无年份） | 候选构成 | 按条数挑会挑中 |
| --- | --- | --- |
| `The.Matrix.mkv` | 32 条 Reloaded + 14 条 Revolutions + 4 条 Revisited，**0 条正主** | ✗ 无论怎么挑都是错的 |
| `阿凡达.mkv` | 32 条《阿凡达 2》(2020) + 18 条《阿凡达》(2009) | ✗ **第二部** |
| `黑客帝国.mkv` | 49 条 The Matrix(1999) + 1 条续集 | ✓ |
| `盗梦空间.mkv` | 50 条 Inception | ✓ |

**结论：年份是准确率的分水岭。** 带上年份，接口能把正主单独挑出来；不带，
"哪个候选是正主"在接口层面就是无从判断的。

### ④ 剧集一模一样，而且更隐蔽

| 搜索方式 | 结果 |
| --- | --- |
| 现在代码走的（片名 + 季集号） | 24 条 / **4 集不同的剧**（混进《Breaking Bad: Original Minisodes》《The Bad Guys: Breaking In》） |
| `imdb_id=959621`（单集编号） | 23 条 / **1 集** ✓ |
| `parent_imdb_id=903747` + 季集号 | 23 条 / **1 集** ✓ |
| 只给 `parent_imdb_id` | 50 条 / **36 集混着**（所以必须配季集号） |

### 两条被实测否掉的路（省得后来人再走）

* **拿片名比对** —— 接口返回的 `feature_details.title` **永远是英文原名**：
  《让子弹飞》→ `Let the Bullets Fly`、《阿凡达》→ `Avatar`、《盗梦空间》→ `Inception`。
  用户的中文文件名跟它**根本对不上**。
* **拿 `release` 里的中文当证据** —— 产出率极低且有假阳性：搜《黑客帝国》50 条里
  只有 1 条 release 含中文，搜《让子弹飞》那 4 条含中文的**全是别的片子**
  （`Bite the Bullet` 的 release 写着「咬紧子弹」）。

## 三、三条根因（都在代码里，都能指出具体行）

| # | 根因 | 证据 |
| --- | --- | --- |
| 1 | **年份解析出来了却从来没传给搜索。** `analyze_filename` 算出 `year`，但 `search()` 压根没有这个参数，三轮搜索一次都没用上；年份只是作为一个普通词混在 `query` 里 | 实测 ①③：加上 `year` 参数，50 条从"全是续集"变成"全是正主" |
| 2 | **接口返回的「这条属于哪部片」一个字段都没读。** 每条候选都带 `feature_details`（`feature_id` / `imdb_id` / `year` / `title`），旧代码完全没提取，排序时**不知道候选是不是你要的那部片**，只能按语言和下载量排 —— 下载量高的续集当然赢 | 实测 ①：Revisited 靠下载量排第一 |
| 3 | **年份还会读错。** `_YEAR_RE.search()` 取**第一个**年份 | `2012.2009.1080p.mkv`（电影《2012》是 2009 年的）读成 2012，实测搜出来是 Coldplay 演唱会 |

## 四、修复（自动那一半）

### 1. `search()` 补上三个参数（`year` / `imdb_id` / `parent_imdb_id`）

最便宜也最见效的一条。三个参数都只在真拿到数字时才传 ——
传 `None` 或空串会被接口当成一个真实的筛选条件，结果是"一条都搜不到"这种最难查的失败。

```python
if _int_or_none(year):
    params["year"] = _int_or_none(year)
imdb = _normalize_imdb(imdb_id)
if imdb:
    params["imdb_id"] = imdb
```

`_normalize_imdb()` 认 `tt0133093` / `" 133093 "` / `133093` 三种写法 ——
接口只认纯数字，但用户从网页上抄下来的通常带 `tt` 前缀。

### 2. `parse_results()` 提取一整组 `feature_*` 字段

```python
"feature_id", "feature_year", "feature_title", "feature_type",
"imdb_id", "tmdb_id", "season", "episode",
"parent_imdb_id", "parent_title",
```

**老结构（响应里没有 `feature_details`）必须退回原样** —— 这一条是本轮
"188 条老用例一条没改就全绿"的原因：新逻辑只在有这批字段时才生效。

### 3. 年份读**最后**一个

```python
years = _YEAR_RE.findall(query)
year = int(years[-1]) if years else None
```

片名里带数字的情况真实存在，而它排在前面（`2012.2009` / `1917.2019`）。
只有一个年份时两种取法结果相同，所以不会伤到常规命名。

### 4. 打分加一项「年份是否相符」

```python
YEAR_MATCH_BONUS     =  300    # 年份相符
YEAR_NEAR_BONUS      =   60    # 差 1 年
YEAR_MISMATCH_PENALTY = -500   # 差 ≥2 年
```

三个数字各有理由，都不是拍脑袋：

* **差 ≥2 年重罚**：同系列的续集年份必然不同，而**续集的片名完整包含正主片名**
  （`The Matrix` ⊂ `The Matrix Revolutions`）—— 靠片名根本分不开，只能靠年份。
* **差 1 年只 +60 不重罚**：**发行年 ≠ 制作年**是真实存在的。实测样本：
  The Matrix Revisited 的字幕 release 写着 "(2002)"，而 `feature_details.year` 是 2001。
  当成"不同片子"剔除会把正主自己剔掉。
* **-500 而不是 -1000**：指纹精确匹配（+1000）是**比年份更硬**的证据 ——
  它意味着"有人拿一模一样这个文件配过字幕"，而 `feature_details` 的年份是
  库里的元数据、本身可能填错。所以年份不符要能压过语言偏好（±600）、盖过下载量
  （≤100），但**不能盖过指纹匹配**（+1000-500 仍是正分）。

拿不到的年份**不奖不罚**："不知道"不等于"不符"。

### 5. 认片 + 锚定重搜（`pick_anchor` / `_anchor_search`）

这是本轮的核心。判据是"片子身份里最硬的那个"，**不是片名**：

| 情况 | 判据 |
| --- | --- |
| 剧集（文件名解析出季集号） | 比 `season` / `episode`（剧集**不需要年份** —— 文件名里通常也没有） |
| 电影 | 比 `feature_year`，容差 1 年 |

筛出"确实可能是这部片"的候选后，按 `feature_id` 聚类取最大簇，
还要求**这簇条数是第二簇的 2 倍以上**（势均力敌 = 分不清，宁可不锚）。
认出来之后，用它的编号**再搜一遍**：

* `imdb_id` —— 电影和剧集单集都用它（实测 50 条 / 1 部片、23 条 / 1 集）
* `parent_imdb_id` + 季集号 —— 剧集的备用路

`find_candidates()` 因此从三轮变四轮：

```
① moviehash 精确 → 命中就到此为止（指纹是最硬的证据，不再锚定）
② 片名 + 年份
③ 去掉首词重试（治 [Group]Movie.2020 这类命名）
④ 锚定重搜（把同系列其他部清干净）
```

### 6. `describe_candidate()` 开头加上「属于哪部片」

状态行现在会写「已匹配 **The Matrix Revolutions (2003)** · 中英双语」。
**用户一眼就能看出配错了** —— 这比字幕画到屏幕上、看几句对不上要早得多。
剧集显示成 `Breaking Bad S01E01` 比只给单集标题 `Pilot` 有用。

## 五、修复（用户那一半：候选列表）

自动那一半有个够不着的角落：**文件名里的年份我拿不到，用户也没法告诉我**。
`阿凡达.mkv` 到底是要 2009 那部还是 2020 那部？除用户之外没人知道。

于是加了 `SubtitleSearchDialog`（底栏【搜索…】）：

```
片名: [The Matrix        ]  年份: [1999]  [搜索]
填上年份能精确得多（同名/同系列片子靠它分开）
┌──────────────────────────────────────────────┐
│ The Matrix (1999) · 中英双语 · 23.976 fps · 下载 4.9 万 │
│ The Matrix (1999) · 简体中文 · 可信来源 · 下载 8.4 万   │
│ The Matrix Revolutions (2003) · 中英双语 · …          │
│ …（滚动）                                             │
└──────────────────────────────────────────────┘
找到 50 条，分属 1 部片子 —— 选一条后点【下载这份】
                                     [下载这份]  [取消]
```

三条设计决定：

* **不锚定。** 用户打开列表就是想"看见所有可能"，锚定会把不属于某一部片的候选
  全滤掉 —— 那恰好是他想看的（比如想确认到底有哪些片子重名）。
  这一点也写进了测试（`手动搜索**不锚定**`）。
* **同一部片的条目连着排**（`group_by_feature`）。实测「阿凡达.mkv」的 50 条里
  《阿凡达》和《阿凡达 2》的条目**交替出现**，用户很难看清这里是两部片。
* **用户的选择优先于我们的打分。** 挑中哪条就下哪条 —— 打分再精细也只是猜。

顺带解决了两件自动永远做不到的事：中文剧名（实测搜「权力的游戏」返回 **0 条**）
可以换个英文名再搜；库里没有的片子也能确认"确实没有"而不是干等。

范式照抄 `ResumeDialog`：`__init__` 只建、`show()` 才 `grab_set` + `wait_window`
（模态等待会把无人值守的回归整轮挂死，测试只建不等）。搜索走
"后台线程 + 队列 + 主线程自我续期的 `after` 轮询"，关窗口时
**必须 `after_cancel`** —— 窗口都销毁了还在排 `after`，只会换来一串
`invalid command name ...`。

## 六、为什么「定不下来就不下」（一个刻意的取舍）

这是本轮唯一一个"少做一步"的设计，值得单独说明。

`looks_ambiguous()` 判断"这批候选能不能自动定下来"，三种情形算定得下来：

1. `pick_anchor` 认出了这是哪部片（年份或季集号对得上）；
2. 候选**全都属于同一部片**（实测「盗梦空间.mkv」50 条全是 Inception）；
3. 同一部片占压倒多数（`AUTO_PICK_SHARE = 0.8`）—— 实测「黑客帝国.mkv」
   49/50 = 98% 放过去、「阿凡达.mkv」32/50 = 64% 拦下来。

**定不下来就一份都不下，直接把候选列表打开。**

为什么宁愿多问一句：

* **下一份错的花的是当天 5 次配额里的一次**（未登录只有 5 次），用户看不出来；
* **搜索不计次**，所以先搜一遍再让人挑这个动作是**免费**的；
* 上下文也能支持这个判断：实测无年份的常见片名（阿凡达、The Matrix）都落在
  这一支里，占手头样本的 2/5 —— **不是罕见情况**。

## 八、踩过的坑

### 1. `candidates=[]` 被真值判断吃掉（测试撞出来的真 bug）

```python
# 错：空列表是 falsy，会被当成"没给候选"，跑去再搜一次
if candidates:
    self._fill(candidates)
else:
    self._start_search()

# 对：`None` 是"还没搜"，`[]` 是"搜过了、一条都没有"，是两回事
if candidates is not None:
    self._fill(candidates)
else:
    self._start_search()
```

表现出来是"空候选时下载按钮没禁用"。顺带把 `btn_ok` 的初始状态也改成禁用。
**这条要是漏了，`looks_ambiguous` 返回空候选的那一瞬间按钮就是可点的。**

### 2. `_int_or_none` 漏挡 `OverflowError`

`int(float("inf"))` 抛的是 `OverflowError`，而 JSON 标准里虽然没有 `Infinity`，
**但 `json.loads` 默认就认它**（一个历史遗留的非标准扩展）。所以接口真可能回一个出来。

### 3. `votes` / `ratings` 原来是裸 `int()`

```python
"votes": int(attributes.get("votes") or 0),      # 实测接口返回 0.0 时侥幸能过
                                                 # 返回 "4.5" 就直接炸掉整条解析
```

全部收敛到 `_int_or_none()`。这个坑一直没爆，只是运气。

### 4. `feature_details.title` 是英文（这条推翻了整个"比片名"的方案）

一度想用"片名 token 相比"来判断是不是同一部片 —— 实测发现接口给的中文片名**永远是英文原名**。
《让子弹飞》的文件名去比 `Let the Bullets Fly`，必然对不上。
于是整个方案改成"年份 + 编号"，片名一个字都不比。

### 5. "无年份时取最大簇"是危险的

这是第二版方案才想明白的：原本打算在没年份时也锚定（按条数挑最大簇），
实测「阿凡达.mkv」那 32 条是**《阿凡达 2》** —— 条数多的是错的那部。
所以 `pick_anchor` 在既没年份又没季集号时**必须返回 `None`**。

### 6. 剧集不需要年份

一开始把"必须知道年份"写进了锚定的硬门槛，接着就发现**剧集文件名里通常没有年份**
（`Breaking.Bad.S01E01.720p.mkv`），那条规则会把整个剧集场景挡死。
剧集的硬判据是季集号。

### 7. `subtitle.discover()` 返回的是 `[(路径, 语种), ...]`

**不是路径列表。** 我的验证脚本当成路径列表用了，`os.path.basename(tuple)` 直接
`TypeError`。这条写在这里是因为它跟第 20 轮那个 `decode_bytes()` 返回二元组的坑
是同一类：**这个模块的函数返回值常常比名字看起来多一样东西。**

## 十一、留给后来人

### 铁律

* **`feature_details` 是整个准确率的根。** 别再从片名想办法 ——
  它的 `title` 永远是英文，中文文件名对不上。认片子只有两条路：
  `feature_year`（±1 年）和 `feature_id` / `imdb_id`。
* **`year` 参数忘不得。** 它一个参数就能让结果从"全是续集"变成"全是正主"。
  测试 ⑯ 里那条 `第二轮**带上了年份**` 就是钉它的。
* **`pick_anchor` 的三道门槛一条都不能松**：必须有年份（或季集号）、
  那一簇要够突出（≥ 第二簇 2 倍）、要有编号可重搜。松掉任何一条，
  「阿凡达.mkv」都会被锚到《阿凡达 2》去。
* **「定不下来就不下」是刻意的**，不是没写完。见第六节。
* **手动搜索故意不锚定**（`search_candidates`）。别顺手给它加上锚定 ——
  用户要的就是看见全部。

### 加语言 / 加判据时改哪儿

* 语言相关的一切还是那三张表（`SEARCH_LANGUAGES` / `LANG_SLOT` / `LANG_RANK`）+ `SLOT_SUFFIX`。
* 年份打分的三个常量（`YEAR_MATCH_BONUS` / `YEAR_NEAR_BONUS` / `YEAR_MISMATCH_PENALTY`）
  和自动挑的门槛（`AUTO_PICK_SHARE`）在模块顶部，都带推导注释。
* **改 `search()` 的参数时记得同步改 `parse_results()` 要读的字段** ——
  这两处是本模块与接口之间唯一的接触面。

### 想快速看懂按这个顺序读

1. `subtitle_online.py` 顶部常量区 —— 三张语言表 + 年份打分常量 + `AUTO_PICK_SHARE`。
2. `analyze_filename` → `movie_hash` → `score_candidate` —— 输入侧。
3. `parse_results` 里那一段 `feature_*` —— 认片子的全部原料。
4. `pick_anchor` → `looks_ambiguous` → `_anchor_search` → `find_candidates` —— 核心算法。
5. `final_player.py` 的 `SubtitleSearchDialog` —— 用户介入那一半。
6. `tests/test_online_subtitles.py` 第 ⑭ 节 —— 一组对照断言，最能说明这轮在干什么。
