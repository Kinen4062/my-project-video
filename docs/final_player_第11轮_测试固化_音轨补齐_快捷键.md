## 一、回归测试固化（本轮最大的收获）

### 为什么这件事排第一

前 10 轮的验证脚本全是"现写、现跑、现删"，都在 `%TEMP%` 里。代价非常具体：

| 轮次     | 做了什么             | 靠什么发现的问题   |
| ------ | ---------------- | ---------- |
| 第 7 轮  | 播放变慢回归           | 事后重写测速脚本   |
| 第 9 轮  | `set_volume` 段错误 | 事后重写压力测试   |
| 第 10 轮 | 拖动后音量丢失          | 事后重写混音通道探针 |

**每改一行播放逻辑，就要把这五类脚本重写一遍。** 而且没有回归保护的改动是裸奔的  
—— 第 7、9、10 轮三次回归全靠用户报上来才发现。

### 结构

```
run_tests.py                 一键入口（每组独立子进程）
tests/
  _harness.py                公共设施：素材、断言、混音通道探针、帧间隔探针、事件泵、键盘焦点
  test_playback.py           功能用例（40 项）
  test_timers.py             定时器泄漏 + "挂起请求必被兑现"不变量（23 项）
  test_shortcuts.py          快捷键与逐帧步进（31 项）
  test_audio_mux.py          转换补音轨（15 项）
  test_speed.py              稳态速度（3 项）
  test_chaos.py              随机交错压力（每种子 7 项）
```

```bash
python run_tests.py            # 默认：3 个压力种子 × 60 次操作（约 3 分钟）
python run_tests.py --full     # 5 个种子 × 80 次操作（发布前跑，约 5 分钟）
python run_tests.py --quick    # 1 个种子 × 40 次操作（改一行看一眼）
python tests/test_playback.py  # 也可以单独跑某一组
```

### 几条硬约定（都是踩过的坑）

- **每组跑在独立子进程里**。Tk / SDL 有全局状态会互相污染；更要紧的是真段错误时  
  能**定位到具体套件**，而不是整轮回归一起陪葬 —— 第 9、10 轮那两个段错误正是靠  
  这个才抓到的。`run_tests.py` 会把"被信号杀掉"的组单独标成 `崩溃`。
- **Tk 必须 `root.update()` 泵事件循环**，`after` 回调不会自己跑。
- **收尾绝不调用 `app.on_close()`** —— 它会 `os._exit(0)`，直接把测试进程掐掉。
- **测试素材运行期生成**：无声的"假 3D 产物"用 `cv2.VideoWriter` 现场造  
  （和程序自己转换产物同源）；连有音轨的素材缺失时也会用 ffmpeg 合成一份，  
  所以套件不依赖仓库里的大文件。
- **量音量只认混音通道值**（ctypes 读 `SDL2_mixer.Mix_Volume`），不认  
  `get_volume()` —— 后者读的是不参与混音的字段，会撒谎。  
  混音器被销毁时返回 `None`，**那个 None 本身就是"混音器没了"的证据**。
- **逐帧步进类断言用像素比对**：拿 `app.current_raw_frame` 和"另一个独立  
  `VideoCapture` 解出的第 N 帧"做 `np.array_equal`，比只看帧号可靠。
- **要发按键就得先抢键盘焦点**（`take_keyboard_focus()`），而且**每次发之前都要重抢**——  
  Tk 在无人值守环境下会反复把焦点清空，缓存一个"已就绪"的布尔量等于没抢。  
  详见第四节「焦点这一关」。

## 二、顺手揪出并修掉的两个真 bug（本轮最有价值的部分）

套件刚写完第一次跑，`连续快速拖动 6 次` 那一组就红了 —— 而且**不是测试写错，是  
真 bug**。诊断脚本（每 200ms 打一次音频状态）把过程拍得很清楚：

```
[拖#1 之后] cal=False dead=False failed=False last_pts=None handoff=True resume=True
[拖#2 之后] cal=False dead=False failed=False frozen=0.00 last_pts=0.0 handoff=True
[拖#4 之后] cal=False dead=False failed=False frozen=0.39 last_pts=0.0 handoff=True
[恢复 +0.75s] cal=False dead=True  failed=True  frozen=1.52 last_pts=0.0   ← 音频被判死
[最终]       cal=False dead=True  failed=True  ...            chans=[(1, 51)] ← 再也没恢复
```

**用户看到的现象**：短时间连续拖几下进度条 → **声音彻底没了**，而且音量滑块从此  
失效（直到重新打开文件）。

### 缺陷 A：交接"等校准"那段里，新的重建请求会被无声丢掉

原 `_do_audio_restart` 只在 `_audio_handoff_thread` 非空时保留请求，注释写着  
"等它取回时再补一次"。但取回路径（`_poll_audio_handoff`）只在**已经交给工作线程**  
时才跑；而"新播放器还在等校准"这段（`_audio_handoff_old` 非空、thread 为空）  
根本不在那条路径上 —— 于是请求被 `self._pending_audio_pos = None` 丢掉了。

**后果**：音频此刻已被 `_suspend_audio_for_seek()` 用 `set_pause(True)` 压住，  
而"恢复"这件事就挂在这个被丢掉的请求上 → **新播放器永远停在暂停态**。

**修法**：

- `_do_audio_restart` 不再丢请求（只在"没文件 / 音频已判死"时才作废）；
- `update_frame` 每帧加一道兜底：**有挂起请求、且没有交接在跑、且不在拖动 → 立刻兑现**。  
  这条把"请求一定会被兑现"变成硬不变量。
- `_poll_audio_handoff_ready` 的收尾判据加上"有待兑现请求"——  
  既然这个新播放器马上要被换掉，就没必要再等它校准（否则白等满 3 秒才出声）。

### 缺陷 B：被"为拖动挂起"的音频，其冻结的 pts 被误判成"死时钟"

死时钟检测（第 11 条修复引入）用来识别无音轨文件（`get_pts()` 恒为 0.0）。  
它的豁免条件是 `is_paused / is_seeking / _scale_pressed` —— 可这三个标志在  
**松手那一刻就恢复 False**，而音频此时仍是"被压住"的状态。

于是"连续快速拖动"里两下之间的空隙被当成"音频在播放却一动不动"，累计  
`AUDIO_CLOCK_STALL_SEC = 1.5` 秒后判死时钟 + `audio_failed = True`  
（后者本来只该用于"确认这个文件没有音轨"）。

**修法**：新增 `_audio_suspended_for_seek` 标记，拖动挂起期间豁免死时钟检测；  
`_mark_audio_live()` 在**所有**"音频重新活过来"的出口解除它  
（交接建出新播放器 / 判定永远不会恢复 / 关闭播放器 / 换文件 / 恢复播放）。

> ⚠️ 这个豁免如果不能可靠解除，就会把**真正的无音轨文件**漏判 —— 而"无音轨"  
> 正是墙钟主时钟的启用条件，漏判就等于第 7 轮"播放变慢"回归复现。  
> 所以 `test_timers.py` 和 `test_chaos.py` 都专门断言了这个标记不会残留。

### 修复后的实测

```
[拖#1..拖#6]  cal=False dead=False failed=False frozen=-1 last_pts=None   ← 不再判死
[恢复 +0.25s] last_pts=12.28  ← 新播放器已经被解除暂停，时钟开始走
[恢复 +0.50s] cal=True         ← 校准完成，音量同步下发
[最终]        cal=True dead=False failed=False chans=[(0,51)]             ← 声音和音量都回来了
```

恢复时间从"永不"变成 **~0.5 秒**。

## 三、3D 转换产物补回音轨

### 问题

`process_video_to_3d` 用 `cv2.VideoWriter`（第 794 行附近）写产物，它**只写视频流**  
—— 所以**视频一转成 3D 就没声音了**。更麻烦的是，程序为此专门维护了一整套  
"无音轨文件"兜底逻辑（死时钟检测、墙钟主时钟、永不调 `set_volume`），  
成了复杂度的一个主要来源。

### 修法

转换收尾调一次 ffmpeg，把**原视频的音轨**并进产物：

```
ffmpeg -i <产物> -i <原视频> -map 0:v:0 -map 1:a:0 \
       -c:v copy -c:a aac -b:a 160k -shortest <临时文件>   →  os.replace()
```

要点：

- `-c:v copy` **不重编码**，只多花一两秒；
- 音轨统一重编码成 aac（原轨可能是任意格式，直接 copy 进 mp4 未必合法）；
- 先写同目录临时文件再原子替换 —— 中途失败也不会毁掉已经写好的无声产物；
- **实现为"锦上添花"**：找不到 ffmpeg / 源文件没音轨 / ffmpeg 失败，  
  一律返回 `False` 且不抛异常，转换本身绝不因此失败（拿到的仍是可播放的无声文件），  
  完成提示里会如实说明有没有带音轨。

### ffmpeg 从哪来（不能想当然）

本机唯一一份 ffmpeg 在 **ffpyplayer 的 wheel 里**  
（`.venv/share/ffpyplayer/ffmpeg/bin/ffmpeg.exe`），**不在 PATH 上**，  
而且只有 FULL-BUILD 轮子才带它。所以 `find_ffmpeg()` 按四条路径找：  
`FFMPEG_BINARY` 环境变量 → PATH → ffpyplayer 自带的（`sys.prefix` 与项目目录两处）  
→ `imageio_ffmpeg` 自带的。找不到就降级。

### 保留旧兜底

"无音轨文件"那一整套逻辑**全部保留**：用户完全可能打开别的无声视频，  
而且 mux 失败时产物就是无声的。`test_speed.py` 专门量了无声素材的速度，  
`test_playback.py` 里那 5 项无音轨用例也都还在。

## 四、快捷键与逐帧步进

原来只有空格（播放/暂停）和 F11（全屏）。现在：

| 按键      | 功能         |
| ------- | ---------- |
| 空格 / K  | 播放、暂停      |
| ← / →   | 上一帧、下一帧    |
| J / L   | 快退、快进 10 秒 |
| ↑ / ↓   | 音量 ±5%     |
| M       | 静音开关       |
| F / F11 | 全屏开关       |
| F1      | 显示快捷键说明    |

底栏最右侧新增一个「快捷键 (F1)」按钮（放 `side=RIGHT`，不挤占本来偏满的主操作区）。

### 三处刻意的设计取舍

1. **焦点冲突一律让路**。滑块与下拉框用方向键改自己的值，所以新增了  
   `ARROW_CONFLICT_WIDGETS`（= 空格冲突列表 + `ttk.Scale`/`tk.Scale`），  
   焦点落在这些控件上时方向键直接放行 —— 否则一次按键会同时改滑块和步进画面  
   （这个坑在空格上踩过，见原审查第 7 条）。
2. **逐帧步进不做音频重建**。差一帧只有 ~40ms，远小于可察觉的音画错位；而本构建  
   重建一次要付 ~0.5 秒。播放态下改为**把主时钟零点挪到新位置**  
   （`_rebase_master_clock()`，只是清掉参考读数，走现成的重新对表路径）——  
   否则同步逻辑会在下一帧把画面拽回原处，看起来就是"按键没反应"。  
   暂停态则只登记位置（`_pending_audio_pos`），恢复播放时统一对齐。
3. **快进/快退直接复用 `finish_seek`**，不另写一套：夹取范围、暂停态重绘、  
   音频对齐、落点记录全都有现成实现，另写一份迟早不一致。

### 帧序号的坑（又踩了一次）

`cv2.CAP_PROP_POS_FRAMES` 给的是**下一帧的序号**（比正在显示的那帧大 1）。  
所以"从当前显示的这一帧走 delta 帧"必须写成 `POS_FRAMES - 1 + delta`，  
否则每按一次都会多跳一帧。`test_shortcuts.py` 用**像素比对**锁死了这个语义。

### 焦点这一关：`root.bind` → `bind_all`

这是**第二次**跑完整回归才暴露出来的，而且暴露的方式很有说服力：  
`--full` 里快捷键那一组 14 项全灭，症状是"按键之后位置纹丝不动"；单独手跑同一组  
却 26 项全绿。同一个脚本、同一个版本，结果不同 —— 环境和代码都有问题。

**环境那一半**：Tk 对键盘事件做"焦点重定向"，事件只交给**当前焦点窗口**，  
没有焦点窗口时**直接作废**，`-window` / `when` 都救不了。刚 `Tk()` 出来的窗口  
`tk.call("focus")` 是空串。前台手跑时窗口顺手抢到了焦点，后台任务跑（重定向到日志）  
就抢不到。所以测试里必须显式抢焦点：

```
[初始]            focus_get=None  tk_focus=''      ← 没有焦点窗口
event_generate    100 -> 100   无效（被丢弃）
[focus_force 后]  tk_focus='.'                     ← 有了
event_generate    100 -> 101   生效
```

两个关键细节：

- 必须是 `focus_force()`，不是 `focus_set()` —— 后者走"请求系统把焦点给我"，  
  没有用户交互时系统会拒绝（实测 `tk_focus` 仍为空）。
- **焦点不是设一次就一劳永逸**：无人值守下窗口不是前台窗口，每轮 `update()`  
  处理到失活消息就会把 Tk 焦点清空。所以每次发按键前都要重新确认一次，  
  不能缓存在变量里（第一版就是缓存了 `can_deliver=True`，于是全组照旧假失败）。

**代码那一半（真缺陷）**：原来全局键走的是 `root.bind(...)`。Tk 的 widget 绑定  
只在"事件投递到的那个控件就是 root 自己"时才触发 —— 用户点过按钮/滑块/下拉框之后  
焦点就留在那个子控件上，事件投给子控件，**root 的绑定根本不执行**。  
于是**只要点过任何控件，所有全局快捷键就集体失灵**（空格从第 1 轮起就有这毛病，  
只是没人"点完按钮再按空格"）。更讽刺的是：那两张"焦点冲突清单"  
（`SPACE_CONFLICT_WIDGETS` / `ARROW_CONFLICT_WIDGETS`）此时**形同虚设** ——  
焦点在冲突控件上时事件压根到不了处理器，让路判断永远走不到。

改成 `bind_all`（注册在 bindtags 最后一级）后，任何控件的事件都会轮到它。  
配套两处调整：

- **让路判断改用 `event.widget`**，不再用 `focus_get()`。后者在窗口没有系统焦点时  
  返回 `None`，`isinstance` 恒为 False → 该让路的没让路；而 `event.widget` 由 Tk  
  直接写明"事件发给谁"，跟系统焦点无关。（顺带：`focus_get()` 答的是"焦点在谁身上"，  
  `event.widget` 答的是"事件发给了谁"，后者才是我们真正要的。）
- 这个改造把"让路"从**巧合**变成了**必要条件**：`bind_all` 的处理器在子控件**之后**  
  执行，"滑块自己动一下"已经发生了，返回 `"break"` 撤不回来，只能靠处理器内部判断。  
  实测确认 `"break"` 仍会中止 `"all"` 标签上排在我们后面的其它绑定。

`test_shortcuts.py` 因此新增两组断言（⓪ 和 ⑦）：绑定必须注册在 `bind_all` 上、  
且**焦点落在普通子控件（Frame）上时 M 键仍然能静音** —— 后者就是这次改造要防的回归。

### 用户实测报"快捷键无反应"→ 让路策略太宽（第二轮）

改完 `bind_all` 之后用户上手就报："**快捷键无反应：空格 / K，← / →，J / L，M，F**"
—— 一次列了 7 个，一个都不响应。先复现，不猜。

写了个"焦点目标 × 按键"的探针表，结果和症状精确对上：

| 焦点在哪 | space | ←/→ | M/J/K/L/F |
| --- | --- | --- | --- |
| 主窗口 / 视频区 | 生效 | 生效 | 生效 |
| **tk.Button / ttk.Button** | 激活按钮 | **全灭** | **全灭** |
| **ttk.Combobox（只读）** | **全灭** | **全灭** | **全灭** |
| ttk.Scale（进度条/音量/视差） | 生效 | **全灭** | **全灭** |
| tk.Entry / Text | 打字优先（应让） | 移光标（应让） | 打字优先（应让） |

**只有"焦点在下拉框上"这一行是 7 个全灭**，和用户描述一模一样 —— 而点过倍速或
模式下拉框之后焦点正好就留在那里。

根因是那两张清单的**粒度错了**：

```python
ARROW_CONFLICT_WIDGETS = SPACE_CONFLICT_WIDGETS + (ttk.Scale, tk.Scale)
#                        ↑ 里面含 Button / Combobox / Checkbutton / Radiobutton
```

把"空格有原生含义的控件"整包当成了"方向键有原生含义的控件"，而且处理器**一张
清单管所有键**。于是只要点过任意按钮或下拉框，←/→/J/L/M/F 就集体让路。

实测把每条边界量清楚之后改写成**有序规则表 + 逐键判断**：

```python
KEY_YIELD_RULES = (
    (ttk.Combobox, _ARROW_KEYS),               # ↓ 弹列表、←/→ 切选项；空格/字母一概不吃
    (TEXT_INPUT_WIDGETS, _ALL_SHORTCUT_KEYS),  # 唯一"全让路"的一类：要打字
    ((tk.Scale, ttk.Scale), _ARROW_KEYS),      # 方向键调值；空格/字母不吃
    ((tk.Listbox,), _ARROW_KEYS + ("space",)),
    ((tk.Button, ttk.Button, ...), ("space",)),  # 只有空格（且是兜底，见下）
)
```

三个必须写下来的坑：

1. **规则表是"第一个类型匹配上就定论"**，不是"没匹配上就继续往下找"。
   第一版写成后者，`ttk.Combobox` 立刻被下面那条更宽的"输入框全让路"吞掉 ——
   因为 **`ttk.Combobox` 是 `ttk.Entry` 的子类**，`isinstance` 对 Entry 也成立。
   这个坑是让路矩阵测试当场抓出来的（4 项 FAIL），改成"类型匹配即定论"才对。
2. **只读下拉框对空格毫无反应**（实测：弹出列表的是 ↓ 键，空格既不弹也不改值）。
   把它算进"空格让路"，等于让空格键变哑巴。这条是实测出来的，看文档推断不出来。
3. **按钮对方向键毫无反应**，但对空格是"激活自己"（实测 `command` 真的执行，
   探针脚本还因此卡在模态文件框上）。

### 规则表之外，还有两个"运行期例外"

有两个地方光靠"控件类型"判断不了，得看**实例身份**或**运行时状态**，
所以单独收在 `_shortcut_should_yield()` 里（表仍然是底座）：

- **进度条不让方向键**（靠 identity：`target is self.scale`）。
  它虽然是 `ttk.Scale`，但语义上是"定位控件"不是"参数控件"，F1 里写的就是
  "←/→ 上一帧、下一帧"。让路给 `ttk.Scale` 的后果实测是：滑块只挪一小格，
  而且**键盘操作不触发 `ButtonRelease`**，定位要等 500ms 的防抖定时器才落地
  —— 既慢又不是逐帧。用户的观感就是"←/→ 没反应"。
  音量/视差滑块照旧让路（它们的方向键动作立即且可见）。
  配套：`step_frame` 的播放态分支要调 `_resume_audio_after_seek_suspend()` ——
  滑块类绑定先把音频 `set_pause` 压住了，而我们把它的防抖定时器取消了，
  `finish_seek` 不会再来，挂起就没人解除（声音会一直哑着）。
- **下拉框分"列表开着 / 关着"两种状态**（靠 `ttk::combobox::PopdownWindow` +
  `winfo ismapped` 实问）。实测只读下拉框在**列表关着**时：
  ↓ 会弹出候选列表（有真实动作），而 **←/→/↑ 完全改不动它的值**。
  所以关着时只让 ↓，另三个归播放器 —— 否则"改完倍速再按 ←/→"要么哑掉、
  要么**又改一次倍速**（每次改倍速要付 0.5 秒音频重建）。列表开着时全让。

改完之后按用户的操作路径复验，**每一种焦点状态下 7 个键全部生效**：

```
焦点在主窗口              空格=OK  K=OK  →=OK  J=OK  L=OK  M=OK  F=OK
用鼠标动过第 1 个下拉框后    空格=OK  K=OK  →=OK  J=OK  L=OK  M=OK  F=OK
用鼠标动过第 2 个下拉框后    空格=OK  K=OK  →=OK  J=OK  L=OK  M=OK  F=OK
点过进度条之后             空格=OK  K=OK  →=OK  J=OK  L=OK  M=OK  F=OK
点过播放按钮之后           空格=OK  K=OK  →=OK  J=OK  L=OK  M=OK  F=OK
```

修复前这张表里，按钮/下拉框/进度条那三行分别有 6~7 个 `--`。

### 顺带把"点过按钮后按空格"也修了

`bind_all` 的处理器在 bindtags 最后一级，返回 `"break"` **撤不掉**按钮已经发生的
动作。所以"让空格在按钮上生效"不能靠让路判断，只能**替换掉类绑定**：

```python
for _cls in ("Button", "TButton"):
    self.root.bind_class(_cls, "<space>", self._on_button_space)  # 做事 + return "break"
```

放在 class 这一级，**在 "all" 之前**执行，直接做播放/暂停并 `"break"`，
按钮的原生绑定根本不会跑 —— 双重动作从源头消失。
代价是键盘用户不能"Tab 到按钮再按空格激活"；本程序是鼠标驱动的播放器，
空格=播放/暂停的一致性是第一直觉，这个取舍划算（回车键仍能激活按钮，没动它）。

### 还给用户留了个"一眼能想到"的恢复动作

让路本身是刻意保留的（否则按 ← 会同时步进画面和移动滑块）。但用户需要一个
不查文档就能做的动作，所以：

- **点一下画面**（`video_container` / `video_label` 的 `<Button-1>`）→ 焦点收回主窗口；
- **选完文件自动收回**（`open_video` 结尾）—— 刚加载完视频，下一个动作几乎一定是播放；
- **窗口重新获得焦点时兜底**：若 Tk 的焦点窗口是空的（此时按键会被直接丢弃），
  把它落到主窗口上（只在"空"的时候补，不打断输入框）；
- **F1 说明里写明**："万一按键没反应：点一下画面即可。"

### 回归防线：焦点 × 按键的让路矩阵

只测"某个键在某个控件上让路"是不够的 —— 用户报的恰恰是"一片按键同时哑掉"。
所以 `test_shortcuts.py` 新增 **⑧ 让路矩阵**：6 种焦点 × 6 个键 = 36 项，
外加"按钮上空格不许有双重动作"。

矩阵用的是**自建实验台**（独立 Toplevel 里的按钮/下拉框/滑块/输入框），
不用 app 自己的控件 —— 测的是让路策略，实验台动起来不会反过来影响播放状态。

⓪ 里还写死了几条**规则守卫**：按钮不让方向键、下拉框不让空格、下拉框不让字母、
按钮的空格类绑定已被替换。谁再把 Button 塞进方向键让路，或把下拉框塞进空格让路，
这几条会立刻红。
