# final_player.py 进度条拖动卡顿 —— 定位与修复记录

**日期**：2026-10-13
**改动文件**：`final_player.py`
**问题**：短时间多次拖动视频进度条十分卡顿，暂停模式下拖动卡顿更严重

---

## 一、结论先行

卡顿的根因是**上一轮"音频同步"修复引入的副作用**：为了让音频能跟随跳转，`finish_seek()` 每次都会**重建整个 ffpyplayer 播放器**，而"关闭旧播放器"这一步是**同步阻塞主线程约 0.5 秒**的。

于是：

| 操作 | 拖动一次的实际代价 |
|---|---|
| 拖动中每次移动 | 若停手超过旧的 200ms 防抖 → 触发一次跳转 → **阻塞 ~0.6 秒** |
| 松手 | 立即跳转 → **阻塞 ~0.6 秒** |
| 暂停态 | 上述 0.6 秒 **再加上**一次重复的 set + 渲染（~0.1 秒） |

"短时间多次拖动"就是把这些 0.6 秒**叠加**起来，所以体感是"拖一下卡一下、越拖越卡"；暂停态因为多一次渲染，所以更重。

修复方向不是"把 0.5 秒变快"（实测这条路走不通，见第三节），而是**让拖动过程中一次都不要付这笔代价**。

## 二、实测数据（本机 .venv，素材为 20 秒的 `test_videos/city.mp4`）

### 2.1 一次跳转的耗时构成

| 步骤 | 耗时 | 说明 |
|---|---|---|
| `_create_audio_player()` | **1.6 ms** | MediaPlayer 构造是异步的，很快 |
| `_close_audio_player()` | **400 ~ 580 ms** | 等读线程退出，**占整个跳转的 ~95%** |
| `cap.set(POS_FRAMES)` + read | **~87 ms** | OpenCV 定位成本 |
| `render_current_frame()` | **~11 ms** | 2D 模式 |
| **完整 `finish_seek()` 一次** | **523 ~ 670 ms** | |

### 2.2 为什么那 0.5 秒消不掉

`close_player()` 内部最终是 `cquit()`，其中 `read_tid.wait_thread(NULL)` 会**无限等待读线程退出**。逐项验证过：

| 尝试 | 结果 |
|---|---|
| 先 `set_pause(True)` 再 close | 580 ms（无改善） |
| 先 `set_volume(0)` 再 close | 570 ms（无改善） |
| 先清空 ffpyplayer 自己的 `get_frame()` 队列再 close | 588 ms（无改善） |
| 创建时加 `vn=1`（禁用它的视频解码） | 399~470 ms（属噪声，无明显改善） |
| 缩短播放时长后再 close（播 0.1s / 4s） | 576 / 550 ms（**与播放时长无关，是固定开销**） |
| **把 close 放到后台线程** | 主线程 **0.7 ms** 返回，但**密集场景下段错误（退出码 139）** ❌ |
| 不用 `close_player`，靠 GC 回收 | 走 `__dealloc__` → 同样调 `cquit()`，同样阻塞 |

**后台线程方案已实测否证，没有采用**——这是本轮最重要的一条"此路不通"记录，避免以后有人再试一遍引入随机崩溃。

### 2.3 拖动卡顿的量化对比（同一进程内跑修复前 / 修复后）

场景：拖动 5 次，每次移动间隔 250 ms（> 旧实现的 200ms 防抖，所以旧实现每次移动之间都会触发一次跳转）。

| 场景 | 每次移动之间的实际耗时 | 拖动中被打断 | 按下到松手 |
|---|---|---|---|
| 修复前 · 播放中 | 743 / 833 / 826 / 838 / 869 ms | **5 次** | **4109 ms** |
| 修复后 · 播放中 | 255 / 255 / 250 / 250 / 253 ms | **0 次** | **1264 ms** |
| 修复前 · 暂停中 | 688 / 815 / 833 / 817 / 816 ms | **5 次** | **3969 ms** |
| 修复后 · 暂停中 | 255 / 252 / 251 / 250 / 251 ms | **0 次** | **1260 ms** |

期望间隔是 250 ms。修复前每次间隔被撑到 600~870 ms（就是那 0.5 秒的重建在事件循环里阻塞）；修复后稳定在 250 ms，**拖动期间零阻塞**。

## 三、改了什么

### 3.1 拖动期间彻底不重建音频（合并 + 挂起）

新增统一入口，替换掉 `finish_seek()` 里的直接重建：

- `_request_audio_restart(seconds)`：登记目标位置 + **防抖合并**（`AUDIO_RESTART_DEBOUNCE_MS = 250`）。短时间内的多次跳转请求只执行最后一次。
- `_do_audio_restart()`：防抖到期后执行唯一一次重建。
- `_suspend_audio_for_seek()`：用户一碰进度条，立刻 `set_pause(True)` 把音频压住（很便宜），同时撤销未执行的待重建请求——避免一边拖一边听到严重错位的旧音频。
- `_flush_pending_audio_restart()`：暂停期间挂起的重建，在**恢复播放时**兑现。

### 3.2 暂停态拖动完全不重建（直击"暂停下更卡"）

暂停时音频本来就不出声，重建纯属白付 0.5 秒。现在只把目标位置记进 `_pending_audio_pos`，等 `toggle_play()` 恢复播放时才重建一次。切倍速在暂停态同样走这条挂起路径。

### 3.3 拖动过程中不跳转（防抖 200ms → 500ms）

`SEEK_DEBOUNCE_MS = 500`，且新增 `_scale_pressed` 状态记录"鼠标是否还按在进度条上"：

- 拖动时每次移动都会重置定时器 → **拖动过程中不会触发跳转**（旧实现 200ms 太短，缓慢拖动时会在拖动中反复触发）；
- 即使定时器真的到期了（用户停手够久），若 `_scale_pressed` 仍为 True，也只**挂起**音频重建，绝不在拖动中付那 0.5 秒；
- 松手（`on_scale_release`）才真正跳转 + 走合并后的重建。

**健壮性补充**：用户可能在进度条上按下、把鼠标拖出控件后才松开，那样 scale 自己收不到 `<ButtonRelease-1>`，`_scale_pressed` 会永远停在 True、音频再也等不到重建。因此在窗口级也绑了一次松开事件作兜底，并在 `on_scale_release` 开头判断 `_scale_pressed`（在别处松手不会误触发跳转）。

### 3.4 暂停态点击不再重复 set + 渲染

暂停态点击进度条时，`on_scale_click` 已经 `cap.set` + 渲染过同一帧，松手后的 `finish_seek` 会用 `_last_jump_frame` 判断并跳过这次重复（省约 100 ms）。

### 3.5 附带优化

- **`vn=1`**：创建音频播放器时禁用 ffpyplayer 的视频解码。画面本来就由 OpenCV 输出，它那条视频流没人消费，等于白烧一半 CPU。实测不影响音频时钟、`ss` 定位、暂停/恢复、无音轨文件（无音轨时 close 仅 5 ms）。
- **窗口标题去重**：拖动时 `on_scale_move` 每秒触发几十次，现在只在秒数真正变化时才改标题。

### 3.6 顺手确认的一个"误会"

上一轮我曾怀疑"程序每帧写 `seek_var` 会触发 `ttk.Scale` 的 command 回调，导致每帧改标题、慢帧率时反复触发跳转"。本轮**实测否证了**：ttk.Scale 的 command 只在用户操作时触发，程序改变关联变量不会回调。为此加的防护（`_syncing_scale`）已删除，没有留下基于错误假设的代码。

## 五、遗留限制（都是底层库的硬约束，不是本次改动引入的）

1. **播放态拖动松手后，音频对齐仍有一次约 0.5 秒的停顿**。它在防抖窗口（250ms）之后发生，且因为请求会被合并，**不会随拖动次数叠加**。要彻底消除只能换掉 ffpyplayer 的音频通道（例如 PyAV 自己解码 + sounddevice 输出），属架构级改动。
2. **跳转精度受视频关键帧间隔限制**：音频定位靠创建时的 `ss`（非精确 seek，回退到前一个关键帧）。常见素材 1~2 秒偏差；`city.mp4` 关键帧只有 0s/12s 所以偏得明显。
3. **暂停态 `get_pts()` 恒返回 0** 是库的读取特性（暂停时主时钟不动），不代表位置错误——恢复播放后时钟立刻正确。
4. **长时间播放的渐进音画漂移**仍未解决（审查报告第 11 条，音画主时钟架构问题），建议单开一轮。

## 六、备忘：本轮确认的"此路不通"

| 想法 | 实测结论 |
|---|---|
| 后台线程 `close_player()` 以避免阻塞 UI | **密集场景段错误（139）**，不可用 |
| 靠 GC / `__dealloc__` 回收播放器 | 同样走 `cquit()`，同样阻塞 |
| 调 `set_pause` / `set_volume` / 清队列 / `vn=1` 来加速 close | 均无改善，close 是与播放时长无关的固定开销 |
| `MediaPlayer.seek()` 定位音频 | 无效（只移动它自己的视频流，音频时钟不动），且暂停态会段错误 |
