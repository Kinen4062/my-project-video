# final_player 播放速度异常慢 —— 根因与修复记录

**现象**：同一个 2D→3D 转换出来的视频，播放速度异常慢（越播越慢，最后近乎爬行）；改动代码之前没有这个问题。

**结论**：这是**上一轮（审查报告第 11 条：音频主时钟同步）引入的回归**。两个原因叠加，都已修掉。

---

## 一、根因：转换产物没有音轨，导致"音频主时钟"被冻在 0

### 1. 转换输出没有音轨

`process_video_to_3d()` 用 `cv2.VideoWriter` 写文件：

```python
out = cv2.VideoWriter(output_path, fourcc, fps, (width * 2, height))   # fourcc = mp4v
```

`cv2.VideoWriter` **只写视频流，不写音频流** —— 也就是说本程序转出来的 3D 视频**全部没有音轨**。

### 2. ffpyplayer 对"没有音轨的文件"不报错，但时钟永远不动

实测（`test_videos/` 与用户目录里的真实产物）：

| 文件 | 有音轨 | `get_pts()` 表现 |
|---|---|---|
| `city.mp4`（原始素材） | ✅ | 0.28 → 1.69，**每 0.1 秒走 0.1 秒** |
| `temp_3d_output.mp4`（转换产物） | ❌ | **恒为 0.0** |
| `output_3d_video.mp4` / `output_bad_3d.mp4` / `我的3D视频1.mp4` | ❌ | **恒为 0.0** |

`MediaPlayer(...)` 对这种文件**构造成功**（不抛异常），只在 stderr 打印
`Failed to open file ... or configure filtergraph`，而 `get_pts()` 从此**永远返回 0.0**。

### 3. 上一轮的逻辑把它当真了

第 11 条的实现是"读 pts → 推算此刻应播第几秒"：

```python
clock = 校准时的视频位置 + (pts − 校准读数) × 倍速
```

对无音轨文件，`pts` 恒为 0，于是 `clock` 被**冻结在 0.25 秒左右**（校准时刻的视频位置）。
而每帧的等待量是

```python
wait = (下一帧媒体时刻 − clock) / 倍速
```

**`clock` 不动、视频位置在涨 → 等待量逐帧线性增长**：第 1 秒 ≈0.8 s/帧、第 2 秒 ≈1.8 s/帧……
表现为"越播越慢，直到几乎卡死"。

**复现实测**（12 秒无音轨素材，6 秒窗口）：

```
墙钟 6.00s / 视频推进 0.88s (22 帧) -> 实际速度 0.147x
每帧等待 ms: 首=14 中位=240 最大=680
等待序列前 12 个: [14, 32, 33, 33, 32, 30, 40, 80, 120, 160, 200, 240]   ← 每帧 +40ms
```

### 4. 为什么上一轮没测出来

端到端测试用的都是 `city.mp4`（**有音轨**），而**程序自己转换出来的视频全都没有音轨** ——
正好是个测试盲区：功能只在自己产出的文件上失效。

---

## 二、顺带补掉：无音轨文件"只能按帧率盲走"，处理一慢就整体变慢

没有音频时钟可对时，原来退回"帧间隔 − 处理耗时"的盲调度 —— 这条路**没有任何追赶手段**：
单帧处理一旦超过帧间隔，画面只会整体放慢。

实测：`2560x720@60fps` 的转换产物盲调度只有 **0.92x**；模拟每帧多花 60 ms 时掉到 **0.54x**。

---

## 三、修法

### 1. 死时钟检测：必须"亲眼见过它推进"才承认是主时钟

`_audio_clock_media_seconds()` 新增两道门槛（`AUDIO_CLOCK_ADVANCE_MIN` / `AUDIO_CLOCK_STALL_SEC`）：

- `get_pts()` 返回合法数字只是必要条件；
- 必须**见过推进量 ≥ 0.05 秒**，校准才算完成；
- 播放期间读数必须持续变化，**连续 1.5 秒完全不变**即判定为"死时钟"
  （`_audio_clock_dead`），本播放器实例永久弃用它；
- 若从头到尾一次都没推进过，说明这个文件根本没有音轨，顺手把音频重建也停掉
  （`audio_failed = True`）—— 反正没有声音可放，重建只会白花每次约 0.5 秒。

计时从"第一次发现读数没变"起算，暂停/拖动这些不读 pts 的时段不会累加进来，不会误杀正常音频。

### 2. 无音轨文件改用"墙钟主时钟"

新增 `_silent_clock_media_seconds()`，返回**"此刻画面应该播到第几秒"**，与音频时钟
**语义完全一致**。于是丢帧追赶、倍速、拖动全部复用 `update_frame` 里同一条代码路径，
只是时钟来源换成墙钟：

```python
target = 零点媒体位置 + (现在 − 零点墙钟) × 倍速
```

- 零点在**起播 / 跳转 / 变速 / 暂停恢复 / 片尾回绕**时重设；
- 滞后超过 `SILENT_CLOCK_MAX_LAG_SEC`（1 秒）视为"中途被卡住"（系统调度、窗口最小化等），
  直接重新对表、不追旧账，免得一次跳掉一大段画面；
- `_master_clock_media_seconds()` 负责"先试音频时钟，没有音轨就退回墙钟"。

### 3. 两道安全网 + 一个我自己引入的 bug

- 主时钟算出的单帧等待**上限 4 个帧间隔**（`FRAME_SYNC_MAX_WAIT_FRAMES`）：
  将来再出现"读数不靠谱"的情况，最多短暂不同步，不会把画面拖成慢动作。
- **修掉本轮重构中自己引入的一处 `TypeError`**：片尾回绕时我把墙钟基准清成 `None`，
  而 `update_frame` 底部紧接着要读它 → 异常打断播放循环（画面直接停住）。
  现在基准改为带 `None` 防御的分支，回绕后是重新对表而不是崩溃。

## 五、两点需要说明（不是 bug）

1. **有音轨视频的画面是"严格跟随音频时钟"的**，这是第 11 条的设计目标。
   本机音频设备时钟实测 **0.987x**（20 秒窗口），所以整体速度 ≈0.988x；
   而画面与音频时钟的滞后量 20 秒只变化 **−0.031 s（无漂移）**。
   在音频时钟准确的机器上就是 1.0x。若强行按墙钟走，反而会让画面和**能听见的**声音错开。
2. **无音轨视频启动的前 1.5 秒**仍走盲调度（这是"死时钟判定"的观察窗口，宁慢勿误杀有音轨的文件），
   之后切到墙钟。所以 5 秒窗口测得的平均值会略低于 1.0x（如 0.966x），**稳态是精确 1.0x**。

## 八、已知限制（都是底层库硬约束，非本次引入）

- 跳转精度受视频关键帧间隔限制（音频定位靠 `ss`，非精确 seek）。
- **有音轨**文件跳转/切倍速仍有 0.2~0.5 秒音频间断（`close_player()` 固定 400~580 ms 阻塞，
  实测无法消除，除非换掉音频通道 —— 那会引入新依赖、影响打包，不建议轻动）。
- 无音轨文件跳转**已无此代价**：不再做无意义的音频重建，实测阻塞从 ~470 ms 降到 **~11 ms**。
