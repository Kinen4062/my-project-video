## 二、需求拆解：用户是怎么一步步走到"只做 ②"的

本轮的用户需求不是一次说清的，而是四句话串起来的。把这条链路写下来，是因为
**它决定了成品长什么样**：

| # | 用户原话 | 我的结论 |
| --- | --- | --- |
| ① | 「这个字幕是根据文本、歌词等自动生成的，还是得自己导入文本之后，才可以进行字幕显示？」 | 现状是**字幕读取器**，不是生成器。`subtitle.py` 只认 `.srt`/`.vtt`，`discover()` 只翻本地磁盘（视频同目录 + `subs`/`字幕` 子目录），全项目搜 `requests`/`whisper`/`asr`/`speech` 一个都没有。 |
| ② | 「工具自动匹配和语言识别生成，这两个情况要怎么做？」 | 拆成两条路：**② 上网匹配**（算指纹 → 查库 → 下载）与 **③ 语音识别生成**（抽音频 → 转写 → 写 srt）。先探家底：**一个新依赖都不用装** —— `requests`、`transformers 4.46.3` + `torch 2.5.1+cu121` + `torchaudio` 全在，CUDA 可用（RTX 4060 Laptop）。 |
| ③ | 「那就只做 2 吧，3 我怕电脑带不动死机」 | **只做 ②**。③ 的顾虑是真实的：转写要占满显存，而 3D 合成也吃 GPU，8GB 显存下 `large-v3` 加深度模型很可能爆（这是我在②的回答里主动提前说过的冲突）。 |
| ④ | 「我已经有 key 了」 | 可以**真机验证**，不必只跑 mock。 |

**当前状态**：② 已实现并有 148 项离线测试覆盖；真机端到端验证待用户提供 key。

## 三、文件分工

### 新增 `subtitle_online.py`：只做五件事

1. **算指纹** `movie_hash()` —— 认片子的唯一可靠手段（比片名准得多）。
2. **搜索** `find_candidates()` —— 三轮降级（见下）。
3. **挑候选** `rank_candidates()` / `score_candidate()` —— 决定"下这一份"还是"下那份"。
4. **下载解压** `fetch()` / `extract_payload()` —— 直链通常是 ZIP，里面才是 SRT。
5. **落盘** `target_path()` / `write_subtitle()` —— **落到视频旁边**，绝不覆盖用户已有文件。

它**不**解析字幕、**不**渲染、**不**碰 Tk。落盘之后交给 `subtitle.py` 现成的
`discover()` / `build()` —— 所以本模块只往外吐**文件路径**，不吐 `SubtitleSet`。
这条边界是本轮最省事的一个决定：字幕的解析/语种识别/编码嗅探一行都不用重写。

### `final_player.py`：只加接线，不加逻辑

改动集中在六处：

1. 导入区加 `import queue` 与 `import subtitle_online`（放在 `import subtitle` 之后、
   `import filedrop` 之前，带注释说明"不引入任何新依赖"）。
2. 新常量 `ONLINE_POLL_INTERVAL_MS = 80`。
3. `_init_subtitle_state` 末尾加三个状态位（**不读文件**，见下）。
4. 底栏 `aux_frame` 加【在线匹配】按钮（左键匹配、右键设置）。
5. 新方法组：`_online_api_key` / `open_online_settings` / `match_subtitles_online` /
   `_online_worker` / `_poll_online` / `_online_done` / `_online_failed`。
6. `on_close` 里停轮询；`show_shortcuts`（F1）补一段说明。

## 四、关键坑（每条都写清"为什么必须这么写"）

### 1. 【架构】HTTP 层必须可注入 —— `OpenSubtitles(session=...)`

搜索 → 挑候选 → 下载 → 解压 → 落盘这条链路里有大量**容易写错又不容易在真机发现**
的东西：字段名、排序规则、重名让路、ZIP 解压、语言代码……它们全都不该依赖
"此刻能不能连上外网"才能验证。

把网络收敛成一个可替换的 `session` 参数之后，整条链路能在测试里跑通，
**网络本身成了唯一的不可测部分** —— 而不是把逻辑和网络搅在一起谁也测不了。
这是本轮所有 148 项断言能在离线下跑的前提。

判据要用 `requests is None`，**不能**用模块级 `HTTP_AVAILABLE`：
后者是 import 那一刻定下的常量，运行时环境变了它不会跟着变
（测试里 `so.requests = None` 它就察觉不到）。

### 2. 【配额真相】先查官方文档，再写代码

动手前查了官方文档和官方论坛，拿到的都是会直接影响设计的事实：

- **认证是两层**：`Api-Key`（属应用/consumer）+ `Authorization: Bearer <JWT>`（属用户）。
- **未登录每 IP 每天只有 5 次下载**；consumer 设成 `Under Development` 可到 100 次/天；
  登录的普通用户 20 次/天、VIP 1000 次/天。
- **搜索不计次**（官方原话："There is no limit for SearchSubtitles"）
  → 所以搜索可以放心打三轮降级。
- 同一 `file_id` 三小时内重复下载不重复计数（重试免费）。
- 计数器按 **UTC 午夜**重置。
- **官方明令禁止把开发者账号密码写死在程序里** → 所以**不做"存密码登录"这条路**，
  只让用户填自己的 key（放 `%APPDATA%/final_player/online.json`，绝不进版本库）。
- **`remaining` 只在 `/download` 的响应里给**（`/infos/user` 要 JWT）
  → 那是唯一能对用户说"今天还剩 N 次"的机会，必须抓住。

### 3. 【数据】中英双语的语言代码是 `ze`，且 `languages` 必须字母序

`ze` = "Chinese bilingual"，是从 OpenAPI 规格里挖到的。它是最值钱的那个语言代码：
字幕组做好的中英对照，**一次下载就让「中英双语」模式有内容**，不用下两份、不浪费配额。

`languages` 参数**必须按字母序**（否则接口报错），所以：

```python
SEARCH_LANGUAGES = "en,ze,zh-cn,zh-tw"
```

### 4. 【数据】`moviehash` 的算法和它那个"反常识"的细节

`moviehash` = **文件大小 + 头 64KB + 尾 64KB 的 64 位小端累加和**。
头尾取样既能区分不同发布版本，又能瞬间算完（不用读整个文件）。

**小于 128KB 时头尾两块会重叠 —— 这是官方参考实现的有意行为，不要"修"它。**
测试里专门用 10 种尺寸跟"朴素实现"逐位比对，就是为了把这个行为钉住。

### 5. 【数据】文件名里的语种标签**决定**播放器认成什么语种

`subtitle.language_from_name` 里文件名标签的优先级**高于内容嗅探**。
所以双语字幕**不能**落成 `电影.zh.srt` —— 那样它只会显示中文那一行，
英文行白白浪费掉。必须落成 `电影.双语.srt`（`language_from_name` 认它是 `both`）。

`SLOT_SUFFIX` 就是干这个的，测试⑥里还有一条**跨模块契约**断言：
直接问 `subtitle.language_from_name("电影.双语.srt")` 认不认，防两边改脱节。

重名让路用 `电影.zh.1.srt`（`target_path` 是纯函数、绝不覆盖用户文件）。

### 6. 【算法】打分函数就是"匹配准不准"的全部

排序规则（数字是我定完又在测试里钉住的）：

| 因素 | 分值 | 为什么 |
| --- | --- | --- |
| `moviehash` 精确匹配 | **+1000** | 压过一切 —— 指纹一样就是同一份片子，别的都是猜 |
| 语言 `ze` / `zh-cn` / `zh-tw` / `en` | +200/200/... | 按目标用户习惯：简体 > 繁体 |
| 帧率相符 / 明显不符 | +120 / **−100** | 帧率不同 = 时间轴会漂，是最常见的"字幕不同步"来源 |
| 可信来源（官方/认证） | +150 | 少踩机翻坑 |
| 非机翻 | +80 | |
| 单片（非剧集包） | +40 | 不用从一整季里挑 |
| 听障字幕 | −30 | 带 `[door slams]`，不是所有人都想要 |
| 下载量 | **封顶**后按千分之一计 | 是口碑不是真理 —— **不能盖过质量判断** |

**搜索三轮**（搜索不花配额，所以随便打）：
① 按 `moviehash` + `moviehash_match=only` 精确搜 →
② 没结果退到按片名搜 → ③ 还没结果去掉首词再试。

第三轮治的是 `[Group]Movie.2020` 这类**括号组名混进搜索词**的情况。

### 7. 【UI/线程】`root.after` **绝不能**从后台线程调用

这是本轮最凶的一个坑。第 ⑪ 节真实窗口测试里，后台线程**完全没收尾**
（`_online_busy` 永远停在 True）。挂 `threading.excepthook` 才拿到确切异常：

```
RuntimeError: main thread is not in main loop
```

而且**后台线程自己抓不住这个异常** —— 结果是按钮永远点不动、只能重启程序。

**修法不是加 try/except**（那只是把按钮继续灰着），而是改成
**队列 + 主线程自我续期轮询**：后台线程只管往 `queue.Queue` 里放结果，
主线程用 `after` 每 80ms 取一次、取完再排下一次。`after` 永远在主线程被调用。

`_poll_online` 还带一个**线程猝死兜底**：如果队列空、线程又 `not is_alive()`，
说明它异常退出了，直接报失败让用户重试 —— 否则按钮就永远转下去了。

### 8. 【UI】fps 必须在主线程读、且**只有真开了视频才传**

```python
video_fps = self.video_fps if self.cap is not None else 0.0
```

`video_fps` 的默认值是 `30.0`，拿它去匹配会让 **23.976 的片子被判成"帧率不符"**
（−100 分，可能因此选错字幕）。传 `0` = "不知道"，打分函数就不会误罚。

### 9. 【UI】`_init_subtitle_state` 只做纯状态初始化、**不读文件**

我一开始写成 `self.online_api_key = subtitle_online.load_config().get("api_key", "")`。
但那个方法的注释明确说"只做纯状态初始化、不碰文件系统"，而且测试基架每次开机都会白读一次。
改成 `None` + `_online_api_key()` **延迟加载**（首次用到才读）。

### 10. 【UI】`on_close` 里必须停掉那个自我续期的轮询

轮询是主线程上**自我续期**的，窗口都销毁了还继续排 `after`，
只会换来一串 `invalid command name "..._poll_online"`。所以 `on_close` 里加一句
`self._online_busy = False`。

### 11. 【数据】下载是 ZIP，判据用**魔数**不用 Content-Type

返回的是临时直链，**通常是 ZIP**（里面才是 UTF-8 的 SRT），而且**直链不带 Api-Key**。
判断是不是 ZIP 用魔数 `PK` 而不是 Content-Type —— **头部会骗人，魔数不会**。

### 12. 【数据】文件名解析取"第一段非技术标记的内容"

**不是**"第一个技术标记之前的内容"。因为发布名常以噪音开头
（`[Subs] Show.S01E03`），按后者会切出空串。

技术标记用发布规范的固定词汇表（`_NOISE_RE`），比"取前 N 个词"稳 ——
片名长度毫无规律（`Up` 和 `The Grand Budapest Hotel` 都是片名）。

**全角括号 `【】（）｛｝［］〔〕` 必须当分隔符**（中文资源极常用），
但**括号内容要保留**（`[阿凡达].2009` → `阿凡达 2009` 是对的），所以不能简单丢弃括号内内容。
年份是有效搜索信息，不丢。

## 五、顺手修掉的两个真 bug（都是测试撞出来的）

### bug ① `write_subtitle` 里把 `decode_bytes()` 的返回值当纯文本用

```python
# 错（功能静默失效，不报错）
text = _subtitle.decode_bytes(blob)
...
data = text.encode("utf-8")

# 对
text, encoding = _subtitle.decode_bytes(blob)   # ⚠️ 返回的是二元组！
if encoding != "utf-8(replace)":
    data = text.encode("utf-8")
```

`decode_bytes()` 返回 `(文本, 编码名)` 二元组（第 18 轮就踩过一次）。
写错之后 `.encode("utf-8")` 抛 `AttributeError`，被外层 `except Exception` **完全吞掉**
→ **"转成 UTF-8"这个功能永远走降级分支、静默失效**。
是测试 ⑥ 的 GBK 用例（写 GBK 进去、期望 UTF-8 出来）把它抓出来的。

顺带加了 `encoding != "utf-8(replace)"` 的保护：带替换字符**硬解出来的"猜出来的文本"**
不能拿回去覆盖原始字节。

### bug ② `subtitle.parse()` 遇到 `\r\r\n` 整份字幕一条都读不出来

`\r\r\n` 被两步 replace 规范成 `\n\n`，而**空行在 SRT 里是 cue 的分隔符**
→ 每个 cue 的文字行前多一个空行 → 全部被丢弃。**不是少几条，是全空。**

这是第 18 轮就存在的缺口，只是从没被那种行尾的素材撞上过 ——
**而网络下载的字幕里冗余回车并不少见**，所以第 20 轮把它暴露出来了。

修法有讲究：

```python
# ⚠️ 只有在 `\r\n` 体系里多余的 `\r` 才是冗余。
# 老 Mac 的换行就是光秃秃一个 `\r`，那种文本里 `\r\r` 是货真价实的空行 ——
# 一起收掉的话两条 cue 会粘成一条（第一版修复就这么踩了）。
if "\r\n" in text:
    text = re.sub(r"\r+", "\r", text)
lines = text.replace("\r\n", "\n").replace("\r", "\n").split("\n")
```

判据用"有没有 `\r\n`"而不是"有没有 `\n`"（后者会把"混着 CR 的 Unix 文本"误判）。
测试里**六种行尾一起验**（标准 CRLF / 冗余 CR-CR-LF / 三连 CR / Unix LF / 老 Mac CR），
就是为了防"修好一个格式、弄坏另一个格式"。

**`FakeSession` 是能离线跑的前提**：它记录每次 `request()` 的 method/url/kwargs，

还能注入失败/非 JSON/状态码。于是"字段名写错""排序反了""解压漏了"这些
最容易错的点全部可验，而不用连网。

+ `_fresh(name)` —— 沙箱删不掉/覆盖不了已有文件，所以每次跑都用一个全新目录。

**16 组全部退出码 0**（11 个具名套件 + 5 个乱序 seed）。第 19 轮同一命令是 15 组 / 369.2s，
本轮多出的 1 组就是「在线字幕匹配」（5.4s）—— 新增功能的测试开销只有 5.4 秒。

> 这个数字是**改完 `_format_quota_reset` 之后**重跑的（第一次全绿是在真机验证之前，
> 374.7s vs 376.3s 两次都录在上面）。两次之间只多了本地时区那一处改动。乱序压力 5 组
> 各轰 80 次 `seek`/`speed`/`pause`/`volume`/`mute`/`open`，结束后逐项检查"没有遗留在跑的
> 交接线程 / 没有遗留待关的旧实例 / 没有挂起未兑现的重建请求 / 没有残留的抢发定时器 /
> 没有残留的『为拖动而挂起音频』标记" —— **本轮音频与时钟一行没动**，全绿是"没碰坏老东西"
> 的证据。

### 真机验证暴露的一处**提示不准**（已修）

配额按 **UTC 午夜**重置（真机原话 `reset_time_utc = ...T23:59:59.999Z`）。对 UTC+8 的用户
那是**第二天早上 8 点**，可状态行说的是「今天还剩 N 次」—— 早上 7 点看到"0 次"、9 点又冒出
"5 次"，像额度在乱跳。

修法：新增 `_format_quota_reset()`，把 UTC 时刻转成本地时钟，状态行变成
「还剩 4 次（08:00 重置）」；读不出来时**退回**原来那句（不硬编）。新增第 ⑪b 节 8 项断言
钉住它 —— 断言**不写死 "08:00"**，而是在测试里独立算一遍本地时刻再比（否则只有 UTC+8 的
机器能过）。实测输出：`'2026-10-14T23:59:59.999Z' -> '07:59'，本机 +0800`。

### 真机验证暴露的一处**隐性依赖**（已钉住）

`_online_done` 用 `explicit_path` 装刚下回来的那份，所以**当次一定生效**。要防的是**下次**
打开视频：那时没人给 `explicit_path`，只剩 `discover()` 自动找。若让路产生的名字排在原名
**后面**，用户就会看到"我刚下的字幕，重开一次就变回老的了" —— 比不生效更莫名其妙。

现在两者一致 —— 但**靠的是 ASCII 顺序凑出来的**：`Movie.zh.1.srt` < `Movie.zh.srt`
（第 9 位 `'1'`(0x31) < `'s'`(0x73)），不是有人设计过。所以在第 ⑥b 节钉了一颗钉子：断言
"重开视频时生效的仍是刚下回来的那份"。哪天有人改了 `target_path` 的让路写法（比如换成
`Movie.zh(1).srt`），这条会**立刻红**，而不是等用户来报"我的字幕莫名其妙变回去了"。

> 顺便说清代价：**用户原来那份从此不再自动生效**（要它回来得删掉新下的、或点【载入字幕】
> 点名）。这个取舍是刻意的 —— 反过来（老的那份始终压过新的）会让人觉得自己刚点的
> 在线匹配白点了，比现在更莫名其妙。

### 已知局限（真机验证确认，但**刻意不修**）

- **按片名搜会撞同名/系列片**：搜 "The Matrix" 排第一的是 `The Matrix Revolutions`。
  这是标题搜索的固有毛病，`find_candidates` 第 1 轮的**指纹精确搜索**就是治它的
  （真实视频文件一定有指纹）。只有"算不出指纹 + 片名又撞车"时才可能配错，
  那时用户再点一次就能换一条。
- `last_total` 会被接口封顶成 **10000**，所以它**不能用来显示"找到多少条"**。
  当前代码只把它记在 `client` 上、没有显示 —— 是对的，别顺手拿去用。

- **配额提示别退回"今天还剩 N 次"**：配额按 UTC 午夜重置，对 UTC+8 的用户那是早上 8 点。
  `_format_quota_reset()` 就是为这个存在的（第 ⑪b 节 8 项断言）；它读不出来时才允许退回。
