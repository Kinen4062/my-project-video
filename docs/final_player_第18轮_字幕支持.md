> 需求原文：
> 「字幕支持。只需要支持中文字幕与英文字幕的双语字幕即可，其他语言字幕可保留

## 1. 先把需求拆成几个能判断的问题

"支持双语字幕"一句话，落到代码里是六个各自可能做错的问题：

| 问题 | 本轮的做法 | 在哪 |
|---|---|---|
| **字幕文件从哪儿来？** | 与视频同名的 `.srt` / `.vtt`，含 `subs/`、`字幕/` 子目录；名字对不上号的可以手选 | `subtitle.discover` / `build` + 底栏【载入字幕】 |
| **"双语"有几种形态？** | 两种都要认：两个文件各一种语言、一个文件里中文一行英文一行 | `SubtitleSet`（一节两个槽） |
| **怎么知道哪份是中文、哪份是英文？** | 先看文件名标签，看不出再看内容 | `language_from_name` / `sniff_language` |
| **一个文件里中英混着怎么分？** | **按行**拆语种，拆完存进每条 cue | `Track.__init__` 里的 `split_by_language` |
| **文字画在哪儿？** | 画进"已经合成好的整屏"，贴着视频画面底部居中 | `_compose_subtitles()`（`render_current_frame` 收尾） |
| **显示哪一种？** | 关 / 中文 / 英文 / 中英双语，四种模式，换文件不重置 | `SUBTITLE_MODES` + 底栏下拉框 + `V` 键 |

至于"其他语言留扩展位"—— 那是**故意**留的，见第 5 节末尾与第 11 节。

## 2. 最要紧的一个决定：字幕画进画面，不做 Tk 控件

需求是"显示字幕"，最直觉的做法是拿一个 `tk.Label` 贴在视频下方。**没这么做**，
而是把文字直接画到"整屏合成完、还没上屏"的那一刻（`render_current_frame` 里）。
三个理由，每个都对应一类将来会来的 bug：

1. **所有让画面变化的路径都会自动带上字幕。** 播放的每一帧、窗口缩放、全屏进出、
   切 3D 模式、暂停态重绘、拖进度条 —— 它们最后全都汇集到同一个方法。
   做成控件的话，"缩放时字幕跟着视频缩放"、"全屏时字幕位置得重算"、
   "暂停态改视差后字幕还在不在"全都要各写一遍，漏一处就是一处错位。
2. **位置能跟着"视频画面那块矩形"走，而不是跟着窗口走。** `_compose_subtitles`
   拿到的是 `video_box = (x, y, w, h)` —— 视频在窗口里真正占的那块。
   有黑边时字幕贴着视频底边，不会飘到黑边里去；全屏时正好在最下面。
   做成控件就得自己算这套几何，而且窗口尺寸一变就全套失效。
3. **截图所见即所得。** 顺手把截图也改成"存上一次真正上屏的那一屏"
   （`_screenshot_frame`），于是"看得到字幕但截图上没有"这种必然会来的报错
   提前消失了。

代价是每帧多一次贴图。实测 **0.10 ms**（944×610 的画布），而四周那圈模糊背景
每 3 帧要 1.67 ms —— 也就是说字幕几乎不花钱。文字本身按内容缓存成图层，
所以只有"换了一句字幕"那一下才付 4.10 ms（见第 7 节的数字）。

## 3. 新模块 `subtitle.py`：四件事，一件都不碰 app

分工照旧（`media_tools` / `depth3d` / `viewfit` / `playlist_store` 一个路子）：
**这个模块不知道播放器存在**，不读 app 状态、不碰控件。它只会四件事：

| 能力 | 入口 | 关键取舍 |
|---|---|---|
| 读文件 | `read_text` | 编码嗅探：BOM → 无 BOM 的 UTF-16 → utf-8 → gbk → big5 → cp1252，**任何输入都不抛** |
| 解析 | `parse` | SRT + VTT 一套正则；坏时间轴跳过那一条，不废整份 |
| 认语种 | `language_from_name` / `sniff_language` / `split_by_language` | 文件名优先；内容是兜底；**日文不许被当成中文** |
| 找文件 | `discover` / `build` | 只认同名前缀；顺序即优先级 |

再加一个只装缓存的 `SubtitleRenderer`（把"若干行文字"渲染成一张带描边的 RGBA
图层）。它算得很轻，但挂在每帧的路径上，所以按内容缓存，理由在第 4 节。

## 4. 核心设计：把"两种双语形态"折叠成一件事

中文圈子的"双语字幕"有两种形态，而且都很常见：

- **两个文件**：`电影.zh.srt` + `电影.en.srt`；
- **一个文件里两种语言**：同一段时间轴上中文一行、英文一行 —— 字幕组最常发的
  就是这一种，文件名常叫 `电影.中英.srt` / `电影.chs&eng.srt`。

如果让上层去分情况讨论"这份字幕是一个文件还是两个文件"，代码会到处是分支。
所以本模块的**唯一形态**是：

> 每条 cue（字幕条目）自己带 `(中文行列表, 英文行列表)`。

`Track.__init__` 一旦解析完就立刻按行拆好语种，之后**再没有人需要关心它原来
是单语还是双语**。上层只剩两个槽：

```python
class SubtitleSet:
    zh = None    # 最多一个中文来源
    en = None    # 最多一个英文来源
```

一个"中英都有"的文件会**同时占两个槽（同一个 Track 对象）**，
而两个单语文件各占一个。于是：

- "显示中文 / 英文 / 中英双语"退化成一个筛选动作（`lines_for(sec, mode)`）；
- 一手一英两个文件时间轴不同步也没关系 —— 中文行从中文轨取、英文行从英文轨取，
  各自按同一时刻查表（`Track.lines_at` 用二分）。

**双语时中文在上、英文在下**：`SUPPORTED_LANGS` 的顺序就是显示顺序，
`lines_for` 按这个顺序拼行，`_render` 从上往下排。

## 5. 认语种：两条路，外加一条保护

### 5.1 先看文件名（优先级最高）

字幕组的命名通常很规矩，比"猜内容"可靠得多 —— 而且**一部片子里英文台词多与少，
跟字幕本身是什么语言没有关系**（中文配音的片子也可能满屏英文专有名词）。

只认**整段 token**（按 `.` `-` `_` 空格 括号 切开），所以：

```
电影.zh.srt 电影.chs.srt 电影.cht.srt 电影.sc.srt 电影.简体中文.srt  → zh
The.Show.2024.en.srt   movie.eng.srt   movie.English.srt          → en
movie.中英.srt   movie.chs&eng.srt   movie.zh-en.srt              → both（两种语言都有）
电影.srt         Enchanted.srt        movie.mp4                   → None（看不出来）
```

`Enchanted.srt` 这一条是故意的：它含 `en` 三个字母，但**不是**一个语种标签。
按 token 切就不会误认。

### 5.2 文件名看不出来才嗅内容

`sniff_language` 数三种字素：汉字（CJK 区）、日文假名、拉丁字母。

### 5.3 日文保护：宁可看不懂，也不糊到画面上

**汉字在中文和日文里长得一模一样**，所以光看汉字根本判不出这份字幕是不是中文。
但这不只是一个理论问题 —— 网上下到日文字幕是常事，而"日文字幕被当成中文显示"
会得到一屏 90% 是汉字的、偶尔夹几个怪符号的东西，用户会以为程序坏了。

所以判据是先看假名：**假名够多（≥3 个且占比不低）就整体判为日文，返回 `None`** ——
不是"不认识的语言"那么简单，是**主动拒绝显示**。这条同时也就成了"扩展位"的兜底：
将来加日文，只需要把它从"拒绝"改成"接住"。

（同理，纯韩文、纯符号的行两边都不收，直接丢。）

### 5.4 逐行拆分的规矩

- 含汉字的行 → 中文。**中文行里夹几个英文单词很正常**（"这个 CPU 很强"），
  把它算成英文会串味；
- 纯拉丁字母的行 → 英文；
- 符号行（`♪`）、假名行 → 谁都不收。

### 5.5 "其他语言留扩展位"具体留在哪儿

需求说其他语言暂不做但要留位置。本模块把这件事做到了**表驱动**：

```python
SUPPORTED_LANGS = ("zh", "en")          # ① 加一个代码
LANG_NAMES = {...}                      # ② 显示名
NAME_TAGS = {...}                       # ③ 文件名标签
# ④ line_language() 里补一条逐行判据
# ⑤ final_player.SUBTITLE_MODE_LABELS 补一个显示名
```

找文件、拆句、查表、绘制、上下顺序**全是按这几张表转的**，一行都不用改。
之所以现在只有两张表，是因为需求明确说了别的语言不考虑 —— 留的是接口，
不是半成品。

## 6. 找文件与加载：几个小决定

- **只认同名前缀**：`电影.srt`、`电影.zh.srt`、`电影.mp4.srt` 都算，
  **同目录里别的视频的字幕不会被认领**（`other.zh.srt` 不会挂到 `movie.mp4` 上）。
  宁可不认领，也不能给用户放一部错片子的字幕。
- **顺序即优先级**：与视频**完全同名**的最优先（最可能是配套的那份），
  其次同在视频目录，最后子目录；同一档按文件名定序（可复现，不是随机）。
- **手选的字幕不受自动开关影响**：`_load_subtitles(video, explicit_path=...)`
  只在"自动找"这条路上看 `subtitle_auto`。用户既然点了名，就该认。
- **手选时不再自动找**：`build(explicit_path=...)` 直接跳过发现流程 ——
  用户的意图优先，而且这样能救那些名字完全不搭的字幕文件（`1.srt` 之类）。
- **坏文件不影响播放**：解析不出任何 cue 的（空文件、只有时间轴的、根本不是字幕的）
  等于"没有字幕"，弹一句提示，视频照常播。

## 7. 性能与缓存：为什么渲染成"图层"而不是每帧画字

带描边的文字每行要画两遍（描边 + 填充），而字幕文字通常连续几十帧不变
（一条字幕两三秒 = 50~75 帧）。做法是把"若干行文字"渲染成一张透明 RGBA 图层，
按 `(行内容, 字号, 可用宽度)` 缓存，每帧只做一次 `paste`。

**实测（本机）**：

| 操作 | 中位耗时 |
|---|---|
| 首次渲染图层（miss） | **4.10 ms** |
| 缓存命中（hit） | **< 0.01 ms** |
| `paste` 到 944×610 画布 | **0.10 ms** |
| （对照）四周那圈模糊背景，每 3 帧一次 | 1.67 ms |

也就是：**换一句字幕付 4 ms，之后每帧 0.1 ms**。按 25fps 算帧预算 40ms，
完全不成问题。

两个细节：

- **字号与宽度都做了量化**（字号取 2 的倍数、宽度取 16 的倍数）。窗口拖动时
  这两个值连续变化，不量化的话一次拖拽就能塞出几十张只差 1 像素的图层，
  把缓存冲干净。测试里专门有一条断言验它（`33 vs 32`、`601 vs 600` 命中同一张）。
- **缓存键里带内容**，所以字幕一换自动就是新图层，不需要任何"手动失效"。

## 8. 本轮踩的坑

### 8.1 嗅探语种时只取了"每条 cue 的第一行"（真 bug，冒烟测试当场抓到）

第一版写的是：

```python
lang = sniff_language("\n".join(cue["lines"][0] for cue in cues))
```

看着像"取代表行"，实际上**双语字幕文件必然被判成纯中文** —— 因为双语文件里
每条 cue 的第一行永远是中文行、第二行才是英文。后果是 `SubtitleSet` 只占了
中文那个槽，选【中英双语】时英文那一行**根本不出现**。

改成所有行拼起来嗅：

```python
joined = "\n".join("\n".join(cue["lines"]) for cue in cues)
```

教训：这种"看起来对、但只在一半的情况下对"的写法，**必须在冒烟阶段就把四种
素材（纯中 / 纯英 / 单文件双语 / 日文）全过一遍**才能发现。第一次冒烟就是
因为打印了 `describe()` 与 `lines_for(..., "en")` 才露出来的。

### 8.2 `%` 格式化撞上 tuple

```python
"...（尺寸 %s）" % (layer.size if layer else None)
```

`layer.size` 是 `(宽, 高)` 二元组，`%` 会把它当成多个参数去填，于是报
`TypeError: not all arguments converted during string formatting`
（在测试的第 ⑦ 节当场炸掉整组）。要包一层：`% ((layer.size,),)`。
测试消息里这种情况特别多，因为经常要打印元组/尺寸。

### 8.3 沙箱里**删不掉旧文件**，于是套件"第一次绿、第二次红"

第一次写素材目录用的是"开跑前 `shutil.rmtree` 清空固定目录"。在开发沙箱里
这一句**静默失败**：

```
os.remove(...)  →  [WinError 5] 拒绝访问
shutil.rmtree(..., ignore_errors=True)  →  静默不删
```

于是上一轮跑剩的 `movie.mp4` 还在，紧接着 `shutil.copy` 想覆盖它，又是
WinError 5 —— 症状是**同一个套件第一次跑绿、第二次跑红**（实测复现，
而且报错点在 `shutil.copy`，看着完全不像"权限"问题）。

改成**每次跑用一个带 pid + 随机串的全新目录**（`_RUN_TAG`）：全程只创建新文件，
一个字节都不覆盖，宿主机和沙箱行为一致。目录由 `run_tests.py` 收尾统一清
（清不掉也无所谓，都在 `%TEMP%` 里）。

顺带说明老套件为什么没踩到：它们复制素材前都写了
`if not os.path.exists(dst): shutil.copy(...)` —— 文件在就跳过，于是"绕"过去了。
新套件不该依赖这种巧合。

### 8.4 模糊背景每 3 帧重算一次，混进了一大坨"与字幕无关"的差异像素

像素级断言最初写成"关字幕 vs 开字幕的差异**全部**落在画面下三分之一"。
它在套件里第一次就过了（6919/6919），但在诊断脚本里冒出过 **69358 个差异、
其中 19333 个不在下三分之一**。

原因不在字幕，而在 `viewfit.LetterboxBgCache`：四周那圈模糊背景**每 3 次渲染
就从当前视频帧重算一次**（`BG_REFRESH_INTERVAL`），重算那一刻整圈黑边都会换掉，
于是差异像素里混进一大块跟字幕无关的东西。

处理方式不是放宽断言，而是**把那个变量消掉**：测试里在像素对比前把
`app._bg.refresh_interval` 设成极大（第一遍算完之后再也没机会重算），
差异就只剩字幕这一个来源。改完数字立刻稳定、可复现：
诊断脚本里那句长字幕是 **13606 个差异像素、全部在字幕带内**（从 y=477 起，
正好是视频画面底部往上一点的位置）；套件里那句短一些，稳定在 **6919 个、
全部在画面下三分之一**。

### 8.5 截图的坑：`ImageGrab` 只拍到了桌面壁纸

按上一轮的做法（抓窗口矩形）截出来的图是**用户的桌面壁纸**，不是程序窗口。
窗口本身是好的：`winfo_viewable()=1`、`wm_state()=normal`、`-topmost` 也设上了，
但进程不在可见桌面上（非交互会话），窗口压根没被合成上去，而 `ImageGrab` 走的是
屏幕 DC。

改用 `app._last_display_image` —— 它就是 `render_current_frame` 收尾留下的"整屏
RGBA"，字幕就画在里面，也是截图功能用的同一份。**不是合成的假图，是程序自己
真正上屏的那一份**，代价只是不含底栏控件（本文开头那张图就是这么来的）。

### 8.6 中文内容里混进 ASCII 双引号（第 16、17 轮都踩过）

写断言消息时写了 `各种"没有字幕"的情况` —— 直接打断字符串常量。
规则重申：**断言消息 / 注释 / 文档里的中文引号一律用「」**。

### 8.7 好消息：Pillow 自带描边，不用手画 8 遍

原计划是"把文字按 8 个方向各画一遍黑字，再画一遍白字"来当描边。实测本机 Pillow
**12.3.0** 的 `ImageDraw.text` 直接支持 `stroke_width` / `stroke_fill`，
一行搞定。

但"支持"不等于"真的画上了"，所以测试里有一条断言专门验它：
图层里**必须同时存在**"不透明的白像素"和"不透明的黑像素"——
只有前者说明描边没生效，白字压在明亮画面上就看不见了。

## 9. 测试分层（`tests/test_subtitles.py`，9 节 96 项）

| 节 | 内容 | 为什么值得单独一节 |
|---|---|---|
| ① | 解析 SRT / VTT | 乱序、坏时间轴、时间写反、CRLF、标签剥离、空文件 |
| ② | 编码嗅探 | utf-8 / BOM / gbk / utf-16 / 无 BOM 的 utf-16 / 二进制垃圾 / 文件不存在 |
| ③ | 认语种 | 文件名 15 例 + 内容 5 例 + 逐行拆分 + **日文必须被拒** |
| ④ | 找同名字幕 | 同目录 / subs 子目录 / 整名当初缀 / **不认领别人的** / 排序 |
| ⑤ | 组装 | 只中 / 只英 / 一中一英 / 单文件双语 / 显式指定 |
| ⑥ | 时间轴查表 | 10 个边界点：左闭右开、空隙、**嵌套字幕的回退**、片尾之后 |
| ⑦ | 渲染层 | 白字 + 黑描边都在、缓存命中、量化、折行、无字体不崩 |
| ⑧ | **端到端 + 像素证据** | 自动认领、四种模式、V 键循环、截图 WYSIWYG |
| ⑨ | 降级 | 没字幕 / 总开关关 / 自动发现关 / 手选垃圾文件，全都不许影响播放 |

**⑧ 是这一套里最要紧的一层，而且它不查变量、只查像素。** 理由很实在：
单元测试全绿、画面上一个字都没有，是完全可能的（算了半天 rows 却没接到渲染那
一步）。所以它做的是：

1. 关字幕 / 只中文 / 只英文 / 中英双语，各渲染一屏，两两求差异像素；
2. 断言**差异全部落在画面下三分之一**（字幕就该在那儿）；
3. 断言**双语比任何一种单语画得都多**；
4. 断言**双语时中文被顶高一截**：`top_row(both)=477 < top_row(zh)=510`
   —— 这条最巧妙，它证明的是"英文插在中文下面，中文被顶上去"这个版式，
   而不是"多画了几个像素"。

## 11. 留给后来人

- **想加一种语言（日/韩/德…）**：只动 `subtitle.py` 顶部那三张表 + 一条逐行判据
  + `final_player.SUBTITLE_MODE_LABELS`。**别在 `discover` / `lines_for` /
  `_render` 里写 `if lang == "zh"`** —— 那几个函数现在是完全按表转的，
  加一个 `if` 就把"表驱动"这件事毁掉了。
- **ASS/SSA 不在本轮范围**：它有样式、定位、卡拉OK 一整套语义，转换器会丢东西。
  真要支持，正确的做法是在 `subtitle.parse` 旁边加一个 `parse_ass`，
  而不是往现有正则里塞特例。
- **改 `_compose_subtitles` 之前先看它的 docstring**：它拿到的 `video_box` 是
  "视频画面那块矩形"，不是窗口。字幕位置的三个常量
  （`SUBTITLE_FONT_SIZE_RATIO` / `WIDTH_RATIO` / `BOTTOM_MARGIN_RATIO`）
  都是相对**它**算的，换成窗口尺寸就会在黑边里飘。
- **`subtitle_enabled=False` 是老套件的安全阀**：字幕挂在每帧渲染的收尾，
  会让"连续切换 <150ms""倍速"那几条耗时断言在临界值上抖。新增套件保持默认关，
  只有确实测字幕的套件才打开。
- **`ROW_STYLE` 是改字色/字号的唯一入口**（现在中英都是白色、英文 86% 大小）。
  想改成"中文白、英文黄"这种搭配，改那一张表就行。
